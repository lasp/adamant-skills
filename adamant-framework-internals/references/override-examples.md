# Custom Model Override Examples

Real override implementations from the Adamant framework, annotated for debugging reference.

## Pattern 1: Init Parameter Type Resolution

**Source**: `product_packetizer/gen/models/product_packetizer_packets.py`

Resolves packet types dynamically from init parameter configuration. Also overrides `final()` to propagate finalization to the resolved model.

```python
class product_packetizer_packets(packets):
    def submodel_name(self):
        return "packets"

    def set_assembly(self, assembly):
        self.assembly = assembly

        # Extract model name from discriminant (init parameter)
        configs = self.component.discriminant.get_parameter_value("Packet_List")
        product_packetizer_package = configs.split(".")[0]
        split_package = product_packetizer_package.split("_Product_Packets")
        product_packetizer_model_name = split_package[0]

        # Resolve model path(s) -- may have multiple matches with specific names
        model_paths = model_loader.get_model_file_paths(
            product_packetizer_model_name, model_types="product_packets"
        )

        # Load and provide assembly context to the resolved model
        self.product_packetizer_model = model_loader.load_model(model_path)
        self.product_packetizer_model.set_assembly(assembly)

        # Replace this submodel's entities with the resolved model's packets
        self.entities = self.product_packetizer_model.packets
        self.ids = [e.id for e in self.entities.values() if e.id]

        # Re-run set_component and set_assembly on base class
        super(product_packetizer_packets, self).set_component(self.component)
        super(product_packetizer_packets, self).set_assembly(assembly)

    def final(self):
        # Propagate final() to the resolved model
        self.product_packetizer_model.final()
```

**Key patterns:**
- `get_model_file_paths()` (plural) when multiple matches possible
- Resolved model needs `set_assembly()` called on it
- Entity replacement: `self.entities = resolved.packets`
- `final()` override to propagate finalization
- Calls `super().set_component()` AND `super().set_assembly()` (unusual -- re-registers with base)

## Pattern 2: Dynamic Command Type Resolution with redo_ifchange

**Source**: `task_watchdog/gen/models/task_watchdog_commands.py`

Replaces command argument types with dynamically generated record types.

```python
class task_watchdog_commands(commands):
    def submodel_name(self):
        return "commands"

    def set_assembly(self, assembly):
        # Call super FIRST (unusual -- most overrides call super last)
        super(task_watchdog_commands, self).set_assembly(assembly)

        # Resolve watchdog list model from init parameter
        watchdog_list = self.component.init.get_parameter_value("Task_Watchdog_Entry_Init_List")
        watchdog_list_package = watchdog_list.split(".")[0].replace("_Task_Watchdog_List", "")

        # Load the autogenerated record type model
        model_name = watchdog_list.split(".")[0] + "_Watchdog_Limit_Cmd"
        model_path = model_loader.get_model_file_path(model_name, model_types=["record"])

        # Declare build dependency -- WARNING: can cause circular dependency
        # if the generator for this type has set_submodels_and_components=True
        redo.redo_ifchange(model_path)

        # Replace command entity with new type
        cmd = self.get_with_name("Set_Watchdog_Limit")
        self.entities["Set_Watchdog_Limit"] = command(
            name=cmd.name,
            type=model_name + ".T",
            description=cmd.description,
            id=cmd.id,
            suite=self,
        )

        # Register the new type with both submodel and component
        self.type_models.append(self.entities["Set_Watchdog_Limit"].type_model)
        self.component.complex_types[
            self.entities["Set_Watchdog_Limit"].type_model.name
        ] = self.entities["Set_Watchdog_Limit"].type_model
```

**Key patterns:**
- `super().set_assembly()` called FIRST (not last) -- order depends on whether you need base data before customization
- `redo.redo_ifchange()` for build dependency on autogenerated types
- Circular dependency risk explicitly noted in comments
- `command()` constructor for replacing individual command entities
- Must register new types in BOTH `self.type_models` AND `self.component.complex_types`

## Pattern 3: Assembly Submodel with Connection Graph Traversal

**Source**: `ccsds_router/gen/models/ccsds_router_table.py`

Inherits from `assembly_submodel` (not `component_submodel`). Resolves routing destinations by traversing the connection graph.

            self.ccsds_router_instance_name

        router_connector = self.ccsds_router_instance_model.connectors.of_name(

- Inherits `assembly_submodel` (for assembly-scope models, not component-attached)
- `assm.get_component_with_name()` for component lookup by string name

- Connection objects have `.to_component.instance_name` and `.to_connector.name`
- Must track `self.dependencies` for cache invalidation
- Not called from `set_assembly()` -- has its own resolution method called by assembly or generator

## Common Override Mistakes

1. **Forgetting `super().set_assembly(assembly)`** -- base class propagation breaks; downstream consumers miss assembly data
2. **Wrong super() call order** -- calling super first vs last changes whether base data is available during customization
3. **Missing `complex_types` registration** -- new types won't be included in generated Ada `with` clauses
4. **Missing `redo_ifchange`** -- model may use stale cache data; but adding it may cause circular dependency
5. **Using `==` instead of `is`** for component comparison -- matches all instances of same type
6. **Not tracking `self.dependencies`** -- cache won't invalidate when upstream changes
